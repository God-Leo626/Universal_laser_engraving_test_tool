# 应用任务审查与修复说明

范围：实际参与工程编译的 `6_hardware/my_task.c/.h`，新增内部纯协议头文件 `6_hardware/app_protocol.h`。原任务文件备份位于 `0_readme/review_backup/6_hardware/`；历史子目录不作为本次编译输入。任务文件保留 GBK、CRLF；纯协议头文件为 ASCII。

## 修复依据与结果

| 原代码中的实际问题 | 修复后的行为 |
| --- | --- |
| USART1 依据本次环形缓冲总长度等于 7/12/13/14 判断命令；分包和多帧粘包不能正确处理 | 按字节增量组帧，二进制依据长度和 XOR，文本依据 CRLF；同一批可以依次处理多条命令，半帧保留到后续接收 |
| USART1 以字符串方式搜索二进制缓冲，使用长度不足或上次残留内容 | 二进制与文本明确分开；完整帧才投递；文本预留结束符，超长整行丢弃 |
| 6/7/8 字节特征值对应的数组只有 12/14/16 字节，hex 转换还需要写入 NUL | 统一使用 17 字节文本缓冲，合并为一个特征值配置函数 |
| 明文 CHIP ID 最多 32 字符，但原数组只有 32 字节 | 唯一码文本容量为 33；完整长度及 hex 字符检查后才组包 |
| `only_len_set` 可把任意小于 0x83 的值作为数组下标，旧命令码又会污染新长度变量 | 唯一码长度仅接受 1..16；旧命令码 0x83..0xFF 单独保存；0、17..130、缺失或错误记录被拒绝 |
| MAC/SN 转换失败后仍继续组包，可能发出前次残留数据；长度与实际 MAC 不符也继续发送 | 收到的 MAC、SN、RSSI 全部校验成功且 MAC 长度与配置严格匹配，才生成完整、初始化的报文 |
| 单次 DMA 不等于完整 NRF 文本；截断、粘包可能错误解析，MAC/SN 分开搜索可能失去配对 | 按 CRLF 保留完整行，MAC 与 SN 在同一条广播内成对解析；至少两条完整广播一致，且当批所有完整广播无冲突才上报 |
| 环形溢出后无法知道文本/帧中间丢字节 | 使用驱动的 dropped 累计计数，变化时清理当前帧和残留队列，重新收集完整数据 |
| RSSI/特征值由两个任务通过多组布尔量共享，等待 NRF 握手时新命令可能覆盖正在设置的内容 | 配置队列保存每条命令快照；USART2 单任务串行处理，消除数据覆盖和 6/7/8 标志组合错误 |
| NRF 应答使用 else-if，一次缓冲中多个成功标志只有首个被处理；旧成功标志可在后续握手复用 | 每条完整应答独立处理；每次发送前重置流和期待状态，仍保留三个 150 ms 等待窗口 |
| 按键读取 Flash 配置的成功标志跨循环残留，缺失长度记录仍可能启动；失败反复自动发送 | RSSI→特征值→长度/旧命令→扫描顺序保留，全部使用当次局部成功状态；错误明确提示，重新确认可重试 |
| Flash 断开读出 0xFF，可被当作 RSSI=-1；保存失败仍表现成功 | 调用新 Flash 状态接口；保存失败输出错误，不发送配置成功二进制回复；读取失败不启动扫描 |
| PC 二进制确认模板仅在读 Flash 流程更新，现场配置流程可能永远无法匹配；迟到确认无事务状态 | 每次上报固定本次命令码，只有等待状态才接受对应完整 XOR 帧或原有 `tesk_ok\r\n` |
| `(time3_count1 % 4)==0` 在 0 和同一个 500 ms 时间片内被重复执行，多次重发 | 首发后按时间片记录，仅在约 2 s、4 s 各重发一次；重发使用首发完整报文快照 |
| 黄色显示阶段在临界区内延时 500 ms，串口任务和接收中断不能正常响应 | 保留黄色 500 ms 展示，使用任务延时让出 CPU；串口确认和计时可继续运行 |
| 栈溢出仅打印后返回；启动任务在临界区内自删，退出代码不能按预期执行 | 异常调用 `board_fatal_error` 停机；全部关键任务创建成功后退出临界区，再删除启动任务 |

## 结构与运行约定

- `app_protocol.h`：与 STM32、FreeRTOS 无关的协议纯函数；负责有界组帧、字段提取、hex/RSSI 校验、上报报文、确认和重发时机。
- USART1 任务：每 10 ms 有界读取 PC 串口；确认立即发布，配置请求进入深度 8 的 FIFO；队列满时报告 `command queue full`，不会悄悄覆盖旧请求。
- USART2 任务：拥有所有运行期 LCD、Flash、NRF 命令操作；按键每 10 ms 处理，广播/配置/进度维持约 100 ms 主业务周期。中断仅负责采集字节、按键事件和计时。
- NRF 的每个 150 ms 握手等待窗口和黄色 500 ms 展示等待按 10 ms 采样、锁存按键，实际动作仍回主循环后执行，避免等待期间漏掉短按或在当前握手中插入另一条 NRF 命令。
- Flash 地址、原二进制命令、XOR 范围、6/7/8 字节特征值、旧/新命令选择、明文/密文显示、黄色→绿色/红色结果和 5 s 超时目的均保持。
- `start_scanning` 要求有效唯一码长度及选用的旧命令码，防止进入无法安全组包的状态；此为原先异常参数路径修复。`use_default_settings` 仍直接转发，接收 `default_settings_ok` 显示成功；接收 `start_scanning_ok` 后锁定配置。原始广播模式也处理扫描状态应答。
- 配置请求现在按接收顺序执行，替代原多组布尔量的固定优先级和覆盖行为；正常上位机逐条命令、等待回复的流程不变。
- 空/超长项目名、无效 RSSI、非法 hex、缺失 CRLF、错误 XOR、缺失 Flash 记录不再静默接受。保存记录使用原格式一次写入，减少重复擦写，但不提供掉电原子事务保证。

## 已完成的主机验证

`0_readme/validation/test_app_protocol.c` 直接包含正式 `app_protocol.h`。使用 `C:/APP/Dev-Cpp/MinGW64/bin/gcc.exe -std=c99 -Wall -Wextra -Werror -O2` 编译，通过以下回归：

- RSSI 二进制帧所有可能的拆分点，连续文本命令，6/7/8 字节特征值多帧粘连。
- 错误校验、超长文本、非法 hex、空/溢出 RSSI、有符号数边界。
- 6 字节 MAC 和 16 字节 CHIP ID 上报报文；旧命令码；SN/RSSI 偏移和 XOR；缓冲前后哨兵不变。
- 长度 0、超大配置值、实际 ID 与配置不一致、目标缓冲不足均不生成上报。
- ACK 命令码与校验校验；同产品匹配、SN 不同拒绝；2 s/4 s 重发时间片只执行一次。
- 一百万字节确定性随机流输入，不越出流缓冲，每个输出帧满足完整协议。

ARM 工程检查由主代理统一执行。主机测试不等于真实 DMA/中断时序或实板验证。

## 必须上板复验的项目与仍存在的协议限制

1. 用真实 NRF 固件确认全部设置应答具有 CRLF；沿用固件原拼写 `cipnertext_set_ok`，未擅自纠正其线上协议。
2. 用单设备、双设备、串口分包/满载、32 字符 CHIP ID 测试两条一致广播的判定；确认异常丢包后能够重新同步。
3. 使用新旧上位机分别测试现场设置、KEY3 读 Flash、原始广播、默认设置、开始扫描、及时/迟到/缺失确认，核对黄绿红显示和 2 s/4 s/5 s 时序。
4. 按键、Flash 擦写和串口满载同时发生时检查响应与丢包统计；硬件故障超时可导致当前业务操作延迟。
5. 现有协议没有事务序号：极迟到、命令码完全相同的 PC/NRF 回复仍无法从线路上区分其所属事务；增加序号必须同步修改上位机/NRF，不在本次兼容改动内。
6. 驱动发送接口返回 void；异常 DMA 失败通过诊断计数报告。PC 结果上报仍依照 5 s 超时重试/判失败，无法证明每条配置请求在物理线路上已成功送达。
7. Flash 原布局没有版本、CRC 或双副本，断电恰逢扇区擦写仍可丢配置；已验证格式和范围，但未改变存储协议。
